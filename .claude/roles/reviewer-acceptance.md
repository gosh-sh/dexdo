# Reviewer: фаза приёмки шага

Этот файл перечитывается ПЕРЕД финальной приёмкой (шаг 6 цикла).
Ревью коммитов тестировщика и кодера — отдельные файлы (`.claude/roles/reviewer-review-tester.md`, `.claude/roles/reviewer-review-coder.md`), выполняются на шагах 2 и 4.

## Приёмка шага — чек-лист

Шаг принимается когда ВСЕ пункты выполнены. `cargo test --workspace` зелёный — необходимое, но НЕ достаточное условие.

### 🔴 0. CHANGELOG (ПЕРВЫМ ДЕЛОМ, до всех остальных проверок)

**BLOCKER — без записи в `CHANGELOG.md` шаг НЕ принимается, PR НЕ создаётся:**

**`CHANGELOG.md`** — запись добавлена ревьюером ДО создания PR. Формат — по датам (см. существующие записи): секция `## [YYYY-MM-DD]`, подсекции `### Added`, `### Changed`, `### Fixed`, `### Removed` с описанием изменений. Не «потом допишу» — СЕЙЧАС.

Самопроверка перед `gh pr create`: «`CHANGELOG.md` содержит запись для сегодняшней даты с описанием этого изменения?» Если нет — СТОП.

Версионирование per-step (Cargo.toml `workspace.package.version`) на текущем этапе **не ведём** — релизного канала нет, единая версия `0.1.0` для всех крейтов. Если эта политика поменяется, пункт вернётся.

### 1. Проверки (блокируют приёмку)

- `cargo fmt --check` — без расхождений
- `cargo clippy --workspace --all-targets -- -D warnings` — без warnings
- `cargo build --workspace` — компиляция без ошибок
- `cargo test --workspace` — все тесты зелёные (test Postgres поднят, см. `README.md#test-postgres`)
- Если в текущем шаге были удалены или переписаны тесты, ревьюер обязан отдельно проверить и явно зафиксировать, что это были тесты на уже запрещённое/удалённое поведение, а не потеря реального покрытия
- Соответствие `docs/api-spec.md` (если шаг трогает публичный контракт — должно быть согласовано с владельцем контракта) и `docs/tech-specs/<spec>.md` там, где шаг затрагивает их зону
- **Документация актуальна (pre-commit doc-sweep)** — перечитай **каждый** файл под `docs/`, корневой `README.md`, и README каждого затронутого компонента. Обнови всё, что инвалидируется branch diff'ом. Это обязательное правило из `AGENT_REQUIREMENTS.md:25-31`, не опциональная проверка.
- Все задачи из промпта выполнены. Каждый пункт промпта обязателен, нет градаций важности
- **Чистая архитектура без костылей.** В branch diff'е (`git diff dev..HEAD`) нет полей/таблиц/функций «на всякий случай», нет дупликации одной информации в нескольких местах, нет shims/fallbacks/wrappers «для совместимости» со старым кодом. Каждый новый артефакт имеет один live use case. Если ревьюер видит «может пригодиться» / «дубль для удобства» / «оставлю на случай rollback'а» — шаг не принимается до удаления

### 1.1 Финальный discovery-pass по PR

Перед созданием PR/перед тем как говорить владельцу «готово», сделай полный correctness-review ветки:

1. `git diff dev..HEAD --name-only` — пойми все зоны изменения.
2. Выпиши из функционального промпта и branch diff удаляемые/переименованные сущности: DB-колонки, config keys, SQL predicates, helper-функции, trait methods, `enum` variants, API filter keys, table names, migration steps, test helpers.
3. Для каждой сущности запусти targeted `rg -n` по релевантным корням (`crates/`, `services/`, `tests/`, `crates/*/tests/`, `services/*/tests/`, `migrations/`, `docs/`, `config/`, `Cargo.toml`, `CHANGELOG.md`).
4. Каждое попадание классифицируй. Разрешены только осознанные остатки: исторические миграции (`migrations/0001_*.sql` и т.д.), rollback/pre-upgrade тесты, changelog/history, новые тесты на отсутствие старого поведения. Неосознанный runtime/test/schema/config остаток = шаг не принят.
5. Для DB/schema changes отдельно проверь: forward migration, down migration (если есть), data preservation, indexes/constraints/FK, все тесты/fixtures которые запускают all-up migrations (`sqlx::migrate!`).

Это не заменяется зелёными тестами. Это финальная защита от «в одном файле осталось старое поле/SQL/fixture».

### 1.2 Финальный cross-model gate

После ручного discovery-pass запусти Codex-валидатор на весь branch diff, а не только на последний коммит:

```bash
VALIDATOR_MODEL=gpt-5.5 VALIDATOR_REASONING=xhigh \
  scripts/validate-implementation.sh "prompts/coder/<текущий-func>-code.md" ".claude/roles/reviewer-acceptance.md" "." "dev" "HEAD"
```

Если текущий цикл был test-only, вместо coder prompt передай tester prompt. Результат `APPROVED` обязателен. `CONCERNS` = шаг не принят; сначала операционный промпт кодеру/тестировщику, потом повтор финального gate.

Финальный gate намеренно запускается на `gpt-5.5` + `xhigh`: это один дорогой прогон на весь branch diff перед PR/merge. Обычные validator-запуски остаются на `gpt-5.4` + `medium`.

Формат валидатора остаётся бинарным: `APPROVED` или `CONCERNS`. Но `APPROVED` валиден только вместе с ручным discovery-pass выше.

### 2. CI

CI на GitHub Actions в DODEX пока нет. Проверки гоняются локально:

```bash
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo build --workspace
docker compose -f docker-compose.test.yml up -d --wait
cargo test --workspace
docker compose -f docker-compose.test.yml down
```

Эта секция вернётся в живой вид, когда CI появится. До тех пор: всё гоняем у себя, не пропускаем `clippy`/`fmt`/`test` ни под каким предлогом.

Для `gh` команд (создание PR, merge) — `GH_TOKEN` из `.env`:

```bash
export GH_TOKEN=$(awk -F' *= *' '/^GH_TOKEN/{print $2}' .env)
```

### 3. 🔴 Уборка перед squash merge — BLOCKER, без неё merge не запускать

Приёмка и «всё зелёное» ≠ готовность к merge. Уборка идёт в **два этапа** с обязательной паузой на ручное ревью владельца между ними.

**Этап A (перед push):** прибрать промпты в `done/`. **Context-файл `prompts/context/<task>.md` остаётся в ветке** — он часть PR'а, на нём опирается ручное ревью владельца.

**Этап B (после ручного ревью владельца):** удалить context-файл. Только тогда уборка завершена и можно мержить.

---

#### Этап A — перед push

**Шаг 3.0 — Самопроверка перед любым git push финальной ветки. Отвечать себе вслух, не «наверное»:**

1. `ls prompts/coder/ prompts/tester/` — на верхнем уровне только папка `done/`? Если есть `.md` файлы — НЕТ, перенеси в done/.
2. `ls prompts/context/` — там есть `.md` для текущей задачи? **ДА — это правильно, оставляем для ручного ревью владельца.** Если `.md` файлов нет совсем — спроси себя, был ли вообще context-файл в этом цикле; если был — найди где потерялся.
3. `git log dev..HEAD --oneline` — коммиты читаемы, чужих хвостов от прошлых циклов нет?
4. `git diff dev..HEAD --stat` — в diff только ожидаемые файлы шага, ничего случайного?

**Шаг 3.1 — Закоммитить всё незакоммиченное:**
```bash
git status   # никаких unstaged/untracked
```

**Шаг 3.2 — Перенести промпты текущего цикла И остатки прошлых циклов в `done/`:**
```bash
git mv prompts/coder/*.md prompts/coder/done/ 2>/dev/null || true
git mv prompts/tester/*.md prompts/tester/done/ 2>/dev/null || true
```
Файлы `.md` на верхнем уровне `prompts/coder/` или `prompts/tester/` = незавершённый долг. Если они лежат там после того как цикл закрыт — их перенёс в `done/` ты.

**🔴 Context-файл `prompts/context/<task>.md` НЕ ТРОГАТЬ.** Он остаётся в ветке. Это намеренно: он сопровождает PR, чтобы владелец и внешний ревьюер при ручном ревью видели полный контекст задачи (диагноз, секции 0a-0d, дизайн).

**Шаг 3.3 — Закоммитить уборку (этап A) и пушить:**
```bash
git commit -m "[reviewer] cleanup: move prompts to done"
git push
```

**Шаг 3.4 — Локальный re-run проверок после push:**
```bash
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo build --workspace
cargo test --workspace
```
Всё зелёное? Только тогда переходи к этапу B. (CI на GitHub Actions появится позже — пока обязательная замена.)

---

#### Этап B — после ручного ревью владельца

**🔴 Шаг 3.5 — Жди ручное ревью владельца. НЕ удаляй context-файл сам.**

Ручное ревью владельца запускается **ТОЛЬКО после зелёного re-run локальных проверок** (см. 3.4). Триггер — владелец явно говорит «прошёл ревью», «годно», «вычищай», «к мержу» или эквивалент. До этого момента:

- context-файл остаётся в ветке
- merge не запускается
- никаких самостоятельных «вычищу заранее, чтобы было готово» — это нарушение

Если локальные проверки зелёные, но владелец молчит — ждём. Пинг с напоминанием допустим, инициатива удаления — нет.

**Шаг 3.6 — Получив явное «ок» от владельца, удалить context-файл:**
```bash
git rm prompts/context/*.md 2>/dev/null || true
```
Context-файлы одноразовые, в `dev` НИКОГДА не попадают. После удаления — история цикла остаётся в `CHANGELOG.md` + PR body + git log. `.txt` валидаторские выводы (`prompts/context/last-*.txt`) трогать не надо — они локальные артефакты валидатора.

**Шаг 3.7 — Закоммитить вычистку (этап B) и пушить:**
```bash
git commit -m "[reviewer] cleanup: clear context after manual review"
git push
```

**Шаг 3.8 — Merge (только по явной команде владельца «мержи»):**
```bash
gh pr merge --squash <PR-номер>
```

**Нарушение этого раздела у меня уже было:** Step 1 saas-plan, context-файл остался в ветке до последнего момента, забыл перенести промпты прошлого цикла. Владелец заметил. Эта секция переписана жёстче. Пропускать = повторять ту же ошибку.

**Дополнительно:** удаление context-файла ДО ручного ревью владельца — нарушение. Владелец не может полноценно ревьюить PR без context-файла. Самостоятельная инициатива «приберусь, чтобы было готово к мержу» = тот же поверхностный режим, что обсуждали в `.claude/roles/reviewer.md` § «Цикл».
