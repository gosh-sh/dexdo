# Reviewer: ревью коммита кодера

Перечитай этот файл ПЕРЕД ревью каждого коммита кодера.

## 0. Загрузи контекст

Перед началом ревью:
1. Открой промпт, по которому работал кодер (файл из `prompts/coder/`, который ты ему дал)
2. Держи его перед глазами — всё ревью идёт относительно этого промпта

## 1. Границы

```bash
git show --name-only <коммит>
```
- ТОЛЬКО файлы вне `test/`. Есть `test/` → **не принимается**

## 2. Соответствие промпту

Открой промпт кодера и пройдись по каждой задаче:
- Каждая задача из промпта реализована? Ни одна не пропущена?
- Код в указанных местах (номера строк из промпта) изменён как описано?
- Нет лишних изменений, которых не было в промпте?
- Версия в `package.json` обновлена (если было в промпте)?
- Секция "Что НЕ менять" соблюдена?

## 3. Прочитай diff

```bash
git diff HEAD~1..HEAD -- apps/worker/src/
```
- Код соответствует реализации, описанной в промпте
- Нет хаков, workaround'ов, закомментированного кода
- Логика понятна и соответствует спеке
- Если кодер отклонился от промпта — понять почему. Отклонение допустимо только если результат функционально эквивалентен И все тесты зелёные
- **Чистая архитектура без костылей.** В diff'е нет полей/таблиц/функций «на всякий случай», нет дупликации одной информации в нескольких местах, нет shims/fallbacks/wrappers «для совместимости» со старым кодом. Каждый новый артефакт имеет один live use case, продемонстрированный в коде. Если кодер ввёл что-то, чему нет немедленного потребителя — не принимается, op-промпт на удаление

### Для шагов с изменением базовой модели: проверь отсутствие запрещённых остаточных паттернов

Если в промпте были секции вида «что удалить», «что не должно остаться», «forbidden patterns», ревью не заканчивается чтением позитивного diff. Ревьюер обязан отдельно проверить, что все запрещённые старые пути, обходные решения и переходные конструкции действительно исчезли из затронутого скоупа. Если основной путь реализован, но запрещённый остаточный паттерн выжил рядом, коммит не принимается.

### Обязательный discovery-pass для correctness

Перед тем как принять коммит кодера, сделай короткий, но широкий поиск по зоне риска:

1. Выпиши из промпта и diff все удаляемые/переименованные сущности: поля конфига, DB-колонки, SQL predicates, helper-функции, enum/state значения, API filter keys, имена таблиц, test helpers.
2. Для каждой сущности запусти targeted `rg -n` по релевантным корням (`apps/worker/src`, `test`, `db`, `docs`, `config.example.json`, `package.json`, `CHANGELOG.md`). Это НЕ опционально для model/schema/API removal шагов.
3. Каждое попадание классифицируй: ожидаемая история/миграция/документация/новый тест или реальный остаток старого поведения.
4. Если найден affected call site/test fixture/rollback path вне позитивного diff — он в скоупе ревью, даже если не был явно перечислен в промпте. Реальный остаток = не принимается.

Косметику, wording и changelog-nit не поднимай как баг. Но stale SQL/test fixture/config/API contract, который сломает рантайм или тесты, — это баг ревью.

## 4. Запусти проверки

```bash
npm run lint
npm run build
npm test
```

Все три ОБЯЗАНЫ быть зелёными.

## 5. Тесты красные → классифицируй перед действием

🔴 **Протрассируй и классифицируй КАЖДЫЙ упавший тест. Без исключений.**

Не "проверю несколько", не "паттерн одинаковый — остальные по аналогии". Каждый упавший тест:
1. Прочитай его код (setup, action, assertions)
2. Протрассируй через НОВЫЙ код кодера — что именно происходит с данными этого теста
3. Определи ПРИЧИНУ падения: какая строка нового кода ведёт себя иначе с данными этого теста
4. Классифицируй (A/B/C)
5. Запиши классификацию с номером строки причины

Только после трассировки ВСЕХ тестов — пиши промпт. Если 20 тестов падают по одной причине и 1 по другой — промпт на "все 20 по аналогии" пропустит этот 1.

**Категории:**

**A. Тест проверяет УДАЛЁННЫЙ код-путь** (функция/ветка/fallback из промпта кодера помечена как удаляемая, и тест ТОЛЬКО её тестирует):
→ Операционный промпт **тестировщику** на УДАЛЕНИЕ теста. Тест закрепляет запрещённое поведение — его нельзя чинить, его надо удалить.

**B. Тест проверяет ВАЛИДНОЕ поведение, но setup идёт через удалённый путь:**
→ Операционный промпт **тестировщику** на UPDATE setup'а (добавить каноническую данные). Поведение остаётся, меняется только способ настройки.

**C. Тест проверяет валидное поведение, setup корректный, код не прошёл:**
→ Операционный промпт **кодеру**. Баг в коде.

**Не принимай фрейминг кодера** ("тесты неправильные", "need mock updates from tester"). Но и не делай обратного — не подбрасывай setup тестам которые тестируют удалённое поведение.

Перед написанием любого промпта перечитай `.claude/roles/reviewer-prompts-coder.md` или `.claude/roles/reviewer-prompts-tester.md` соответственно.

## 6. Трассировка новых тестов через код

Для каждого НОВОГО теста (написанного тестировщиком в этом цикле):
1. Пройди строка за строкой через реальный apps/worker/src/ код с mock значениями из теста
2. Убедись что mock objects поддерживают execution path в НОВОМ коде кодера
3. Реальная логика действительно выполняется, а не перехватывается раньше
4. Тест проходит по правильной причине — из-за корректной реализации, а не из-за совпадения

Ноль падений при массовых изменениях — red flag, требующий особого внимания.

## 7. Cross-model валидация

После завершения ревью запусти с функциональным промптом текущего цикла.

**Важно:** 4-й параметр = base ref для diff. Передавай `HEAD~1` чтобы валидатор видел ТОЛЬКО коммит кодера, а не весь ветковый diff от main.

```bash
scripts/validate-implementation.sh "prompts/coder/func-...-code.md" ".claude/roles/reviewer-review-coder.md" ":!test/" "HEAD~1"
```

**Запускать ТОЛЬКО в foreground** (без `run_in_background`). См. `.claude/roles/reviewer.md` § «Validation-скрипты — ТОЛЬКО foreground»: codex буферизует stdout, фоновый запуск даёт «тишину = жив?» и срывает цикл при rate-limit.

APPROVED обязателен. При CONCERNS — операционный промпт кодеру и перезапуск валидации. Без лимита итераций.

`APPROVED` от валидатора — бинарный gate, но не повод выключать голову. Если твой ручной discovery-pass нашёл проблему, а валидатор сказал `APPROVED`, верь фактам из кода и пиши операционный промпт.
