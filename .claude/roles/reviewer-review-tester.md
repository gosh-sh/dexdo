# Reviewer: ревью коммита тестировщика

Перечитай этот файл ПЕРЕД ревью каждого коммита тестировщика.

## 0. Загрузи контекст

Перед началом ревью:
1. Открой промпт, по которому работал тестировщик (файл из `prompts/tester/`, который ты ему дал)
2. Держи его перед глазами — всё ревью идёт относительно этого промпта

## 1. Границы

```bash
git show --name-only <коммит>
```
- ТОЛЬКО файлы в `test/`. Есть что-то вне `test/` → **не принимается**
- Менял ТОЛЬКО тесты, явно указанные в промпте. Изменил неуказанный тест → **не принимается**
- Существующие тесты НЕ изменены (если в промпте не было явного указания на изменение)

## 2. Соответствие промпту

Открой промпт и пройдись по каждому тест-кейсу:
- Ни один тест, не содержащийся в промпте, не был изменен?
- Каждый тест из промпта реализован? Ни один не пропущен?
- Имена тестов соответствуют указанным в промпте?
- Setup каждого теста соответствует описанному в промпте (моки, данные в БД, начальное состояние)?
- Assert'ы проверяют именно то что указано в промпте (значения, количество вызовов, содержимое сообщений)?

Если тестировщик добавил тесты, которых НЕ было в промпте — проверь что они не ломают логику и не конфликтуют с существующими.
Если в промпте было явно указано удалить или переписать существующие тесты, которые закрепляют уже запрещённое поведение, проверь что это реально сделано и что старое ожидание не осталось жить под другим именем. Оставленный старый тест в таком случае = непринятый коммит тестировщика.

## 3. Качество каждого теста

Для каждого нового теста (не "пробежал глазами", а прочитал код):
1. **Сценарий** — какой именно сценарий из промпта покрыт?
2. **Setup** — реалистичное состояние? Все записи/связи, которые были бы в проде к этому моменту?
3. **Моки** — значения моков соответствуют описанным в промпте? Внешние сервисы замоканы ТОЛЬКО на границе HTTP-вызова, внутренняя логика — без моков?
4. **Assert'ы** — проверяют реальные значения? Не просто "не null" / "не упало"? Проверяют именно то поведение, которое описано в промпте?
5. **Причина прохождения** — тест проходит по правильной причине, а не случайно?
6. **Чистая архитектура без костылей.** В тестовом коде нет helper'ов / fixture'ов / setup'ов «на всякий случай», нет дупликации одного и того же setup'а в нескольких местах, нет wrapper'ов для совместимости со старыми тестами. Каждый артефакт имеет один live use case. Тестировщик добавил helper, который никем не используется кроме одного теста и не упрощает чтение — не принимается

## 4. Моки не обрывают code path

Протрассируй каждый тест мысленно через будущий код (описанный в промпте кодеру):
- Мок не перехватывает вызов раньше, чем нужно?
- Execution path доходит до проверяемой логики?
- Если мок использует `mockResolvedValueOnce` — порядок вызовов правильный?

## 5. Совместимость с существующими тестами

Прикинь: сможет ли кодер написать код, который пройдёт новые тесты И все существующие? Если моки нового теста конфликтуют с паттернами существующих тестов — исправить сейчас промптом тестировщику, а не после кодера.

### Обязательный discovery-pass по старым тестам

Перед принятием коммита тестировщика проверь не только новые тесты, но и остатки старого поведения:

1. Выпиши из промпта удаляемые/переименованные сущности: DB-колонки, config keys, SQL predicates, helper-функции, enum/state значения, API filter keys.
2. Запусти targeted `rg -n` по `test`, а для schema/model changes также по `db` и `apps/worker/src` ровно по этим сущностям.
3. Все старые тесты/fixtures с найденными сущностями классифицируй:
   - старое запрещённое поведение, которое надо удалить/переписать;
   - валидный pre-migration/pre-upgrade сценарий, который надо оставить;
   - unrelated текст/комментарий.
4. Если prompt тестировщика не перечислил существующий тест или fixture, который после кода начнёт падать или продолжит закреплять запрещённое поведение, коммит тестировщика не принимается. Сначала операционный промпт тестировщику на покрытие/переписывание.

Нельзя принимать “зелёные новые тесты”, если рядом остались старые fixtures, которые all-up schema/API больше не поддерживает.

## 6. Полнота покрытия

После прочтения ВСЕХ тестов сверь с промптом:
- Все тест-кейсы из промпта реализованы?
- Граничные случаи из промпта покрыты?
- Есть ли критический сценарий, который пропущен? Если да — промпт тестировщику на доработку

## 7. Cross-model валидация

После завершения ревью запусти с функциональным промптом текущего цикла.

**Важно:** 4-й параметр = base ref для diff. Передавай `HEAD~1` чтобы валидатор видел ТОЛЬКО коммит тестировщика, а не весь ветковый diff от main.

```bash
scripts/validate-implementation.sh "prompts/tester/func-...-tests.md" ".claude/roles/reviewer-review-tester.md" "test/" "HEAD~1"
```

**Запускать ТОЛЬКО в foreground** (без `run_in_background`). См. `.claude/roles/reviewer.md` § «Validation-скрипты — ТОЛЬКО foreground»: codex буферизует stdout, фоновый запуск даёт «тишину = жив?» и срывает цикл при rate-limit.

APPROVED обязателен. При CONCERNS — операционный промпт тестировщику и перезапуск валидации. Без лимита итераций.

`APPROVED` — бинарный gate. Но если ручной discovery-pass нашёл пропущенный существующий тест/fixture с реальным риском, не принимай коммит даже при `APPROVED`.
