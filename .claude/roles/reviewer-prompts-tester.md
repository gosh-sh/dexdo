# Reviewer: промпт тестировщику

Функциональные промпты (диагноз, дизайн, написание промптов) → ultrathink + plan first. Ревью коммитов, приёмка, операционные промпты → обычный режим. Застрял в цикле → ultrathink.

Перечитай этот файл ПЕРЕД каждым написанием промпта тестировщику.

## Запреты

Запрещено править существующие тесты если не было изменений в спеках, которые их ломают. Если упал существующий тест - это баг в коде.

Если текущий шаг или обновлённая спека прямо запрещают старое поведение, ревьюер обязан в промпте тестировщику не только запросить новые сценарии, но и явно перечислить существующие тесты, которые нужно удалить или переписать, потому что они закрепляют уже запрещённую модель. В шагах, где меняется базовая модель работы, сохранение таких тестов считается ошибкой ревьюера.

Запрещено добавлять тесты ради количества, симметрии матрицы или "красивого покрытия".

Запрещено добавлять тесты на:
- тривиальные геттеры
- passthrough-обёртки без собственной логики
- синтаксические вариации без изменения поведения
- дубли уже покрытого риска
- искусственные комбинации из матрицы без нового эксплуатационного риска

Каждый новый тест обязан отвечать на вопрос:
**какой реальный баг он поймает, который сейчас не ловится существующими тестами?**
Если ответа нет — тест не нужен.

**Чистая архитектура без костылей.** Промпт тестировщику не должен предписывать создавать helper'ы / fixture'ы / setup'ы «на всякий случай», дублировать один и тот же setup в нескольких файлах или строить wrapper'ы для совместимости со старыми тестами. Каждый артефакт в тестовой зоне (`tests/`, `crates/*/tests/`, `services/*/tests/`, inline `#[cfg(test)]`), который промпт просит добавить, должен иметь один live use case. Если в задании всплывает «может пригодится» или «дубль для удобства» — переформулируй или убери.

## Сценарное покрытие

### Приоритет рисков (обязателен)

Перед написанием промпта тестировщику ревьюер обязан разметить риски задачи:

- `P0` критично: рассогласование стакана/балансов, потеря/двойное исполнение ордера, рассинхрон on-chain ↔ индексер, проигнорированный реорг блокчейна, утечка приватных ключей/секретов
- `P1` высокий: неверные переходы статуса ордера, ретраи к chain RPC без идемпотентности, потеря событий при рестарте индексера, ошибки миграций, нарушение fail-closed валидации DTO
- `P2` средний: локальная логика с заметным эффектом
- `P3` низкий: косметика, тривиальные helper-кейсы

Промпт обязан покрыть `P0/P1`.
`P2` — только точечно.
`P3` — не покрываем.

### Матрица сценариев

Перед написанием тестового промпта построй матрицу.

**Важно:** полная матрица обязательна только для:
- state machine
- scheduler / tick-логики
- retry / escalation
- startup / restart / recovery
- persistence / migration
- delivery / idempotency
- pipeline lifecycle
- user blocking/unblocking logic

Для локальных unit-функций — только релевантные измерения. Не добивать матрицу ради симметрии.

**Измерения:**
1. **Хранилище**: пустая БД (свежая миграция), частичные данные (pre-reconcile markets), повреждённые/inconsistent данные (например, `last_reconciled_at` без `orderbook_address`)
2. **Время**: в прошлом (давно / недавно), сейчас, в будущем, граничные значения (timestamps на границах lifecycle, миллисекундные интервалы)
3. **Конфигурация**: валидная, невалидная, частичная, отсутствует (`config/*.yaml`)
4. **Внешние сервисы**: chain RPC / GraphQL gateway доступен, таймаут, отказ, частичный отказ, расхождение между event stream и chain state
5. **Жизненный цикл**: первый тик индексера, N-й тик, рестарт, рестарт после длинного простоя, реорг
6. **Данные**: пустые, нормальные, граничные (null, пустые строки, uint256 на границах), большие объёмы (пагинация markets/orders)
7. **Состояния**: переходы между статусами (markets lifecycle PENDING→UPCOMING→…→RESOLVED; order NEW→PARTIALLY_FILLED→FILLED), артефакты на каждом этапе, «тихие» промежутки между событиями

**Процесс:**
1. Сначала перечисли `P0/P1` риски
2. Перечисли релевантные измерения
3. Построй таблицу сценариев
4. Отметь покрытые существующими тестами
5. Промпт тестировщику — ТОЛЬКО непокрытые и действительно важные сценарии
6. Не отправляй промпт пока риски `P0/P1` не покрыты

### Уровни тестирования

1. **Unit-тесты** — только для нетривиальной чистой логики
2. **Интеграционные** — основной уровень для бизнес-поведения
3. **Fault tolerance** — обязателен там, где есть внешние зависимости/ретраи/рестарты
4. **Observability** — только для критичных диагностических событий
5. **Lifecycle** — обязателен для scheduler/state-machine/retry

Если сильный интеграционный тест уже ловит риск — не добавляй несколько слабых unit-тестов на тот же риск.

Внешние сервисы (chain RPC, GraphQL gateway) мокаются только на границе HTTP-вызова через `wiremock-rs`. Вся внутренняя логика до точки исходящего HTTP — без моков. Postgres НЕ мокается — используется `sqlx::test` с реальной disposable БД.

Самопроверка: "Если кодер реализует фичу в неправильном слое, поймает ли тест?" Если нет — тестов недостаточно.

### Обязательные сценарии (если применимо)

**Lifecycle (для компонентов с циклом/тиком, прежде всего индексер):**
- Fresh start → первый тик → нет данных → события появляются → следующий тик → результат
- Рабочая система → рестарт → resume с `indexer_cursors` → нормальная работа
- Отказ chain RPC → retry с backoff → восстановление → успех
- Первый тик спроецировал событие → второй не дублирует (`raw_events.msg_id UNIQUE` идемпотентность)
- Реорг блокчейна → обработка изменения цепочки

**Startup (для сервисов с background-loops):**
- Fresh DB (первая миграция), Non-fresh DB (рестарт с накопленной историей), рестарт после длинного простоя
- Свежие миграции при старте через `sqlx::migrate!`
- Смена конфигурации между рестартами (`SIGHUP` для indexer)

**Config:**
- Пустой (дефолты), невалидный yaml, частичный, смена при рестарте

**Граничные значения:**
Для каждого числового условия (`>`, `>=`, `<`, `<=`): значение ровно на границе, 1 единица внутри, 1 единица снаружи.
Для uint256 в схеме (`numeric(78,0)`) — граничные значения uint128/uint256.
Для временных окон — то же, с точностью до секунды/миллисекунды.
Применять только там, где это реально влияет на поведение системы.

**Time-zone-зависимая логика:**
- Тестируй UTC (канон) и одну non-UTC таймзону, если код туда заглядывает.
- Добавлять только если логика реально зависит от таймзоны клиента/сервера.

**State machine (компоненты с автоматом состояний):**

Матрица сценариев покрывает отдельные состояния. Баги живут в **переходах**.

1. Перечисли ВСЕ состояния и ключевые переходы между ними
2. Тест на КАЖДЫЙ ключевой переход: setup = состояние ДО со всеми артефактами которые были бы в проде → action → assert = состояние ПОСЛЕ
3. Setup ОБЯЗАН быть реалистичным — включать все записи/связи, накопленные к этому моменту жизненного цикла. Неполный setup для позднего состояния — бесполезен
4. Для переходов с задержкой — тестируй "тихий" промежуток: тик сразу после перехода, тик посередине. Assert: ничего не произошло

Самопроверка: "Если кодер обработает сущность в неправильном состоянии, какой тест поймает?"

## Правила качества

### 🔴 Изучи реальное API ПЕРЕД написанием промпта (не при приёмке)

Это делается ДО создания промпта тестировщику, а не после. Если мок написан по памяти и оказался неверным — потеряна целая итерация (тестировщик + кодер + фикс).

Проверь реальные типы, сигнатуры, поля через `Cargo.toml`-зависимости (документация crate на docs.rs), реальный код контрактов (`contracts/`), `docs/api-spec.md`, или прямой вызов эндпоинта. Убедись что ВСЕ поля, которые ты указываешь в `wiremock` ответе, реально существуют в API. Не придумывай структуру по памяти. `serde_json::Value` без типизации, `.unwrap()` в test-setup без обоснования, или передача raw JSON-строки вместо типизированных struct'ов = красный флаг, что типы не проверены.

### Трассировка кода перед моком

Протрассируй функцию целиком с предлагаемыми значениями мока. Проверь что мок не обрывает code path, который тест должен проверять.

### 🔴 Массовая замена (sed/regex или rename X→Y)

Прогони паттерн мысленно на реальной строке из репо ДО отправки и перечисли в промпте все формы X в Rust: `use`-импорт, `mod`-декларация, `#[derive]`-атрибут, имя в `Cargo.toml`-зависимостях, имя в SQL-миграциях (`migrations/*.sql`), имя в config-yaml ключах, имя в test-fixture'ах (`.rest`-файлы), имя в `#[sqlx::test]` метках. Не забывай trait/struct/fn/enum/const формы — это разные синтаксические гнёзда в Rust.

### Полный скоуп при фиксе регрессий

Нашёл регрессию в одном тесте — найди ВСЕ тесты с аналогичным паттерном (grep по имени функции, значениям, мокам). Промпт покрывает все затронутые тесты, не только первый найденный.

### 🔴 Grep по всем call sites перед промптом на фикс

Фиксишь вызов функции X → `rg X` по всей кодовой базе. Каждый call site — потенциально тот же баг. Промпт ОБЯЗАН покрывать ВСЕ call sites, не только тот что нашёл владелец. Промпт без полного grep = неполный промпт = повторный баг-репорт от владельца = провал ревьюера.

Для schema/model/API/config removal это шире, чем grep по функции. Обязателен targeted `rg` по всем сущностям из изменения: DB column, SQL predicate, config key, API filter key, helper, enum/state, table/index name. Ищи минимум в тестовых локациях (`tests/`, `crates/*/tests/`, `services/*/tests/`), и для миграций/схемы также в `migrations/`, `crates/`, `services/`, `docs/`, `config/`. Промпт тестировщику обязан перечислить старые тесты/fixtures, которые надо удалить/переписать, и явно назвать pre-migration/rollback места, где старое поле/путь остаётся легитимным.

Чеклист перед отправкой промпта:
1. Если промпт меняет тестовую инфраструктуру (mock, helper, fixture) — grep по всем тестовым файлам где она используется. Каждое использование = изменение в промпте
2. Если промпт для кодера: `rg -n <имя_функции> crates/ services/` — список всех вызовов
3. Для каждого call site: тот же баг применим? → включить в промпт
4. В промпте явно перечислить ВСЕ места с номерами строк

### 🔴 Grep по тестам для каждого удаляемого code path

Промпт кодеру удаляет запрос/функцию/ветку X → `rg -n 'X' tests/ crates/*/tests/ services/*/tests/`. Для каждого найденного теста:
- Тест сидит на данных, которые работают ТОЛЬКО через удаляемый путь? → включить в промпт тестировщику
- Тест закрепляет запрещённое поведение → DELETE
- Тест проверяет легитимное поведение, но setup идёт через удаляемый путь → UPDATE (добавить canonical setup)

Не забывай inline `#[cfg(test)] mod tests` внутри `crates/*/src/*.rs` и `services/*/src/*.rs` — они тоже тесты, и удаление кодером соседней функции в том же файле может потребовать обновления.

Кодер не трогает test-локации (кроме inline-блоков по явному указанию). Если ревьюер не заложит обновление тестов в промпт тестировщику — кодер не сможет удалить код без красных тестов и обойдёт промпт.

### 🔴 Op-промпты тоже требуют grep-анализ

Операционные промпты пропускают cross-model валидацию, но НЕ пропускают grep-анализ тестов для удаляемых код-путей. Перед каждым op-промптом тестировщику, который добавляет setup к упавшим тестам:
1. Спроси: "Этот тест тестирует удалённый код-путь или валидное поведение?"
2. Если удалённый → DELETE, не UPDATE
3. Если валидное, но setup идёт через удалённый путь → UPDATE
Подбрасывать canonical-данные к тесту на удалённый fallback — та же ошибка, что и оставить мёртвый fallback в коде.

### Комплексное покрытие с первого промпта

Покрытие должно быть достаточно полным по `P0/P1` с первого промпта.
Реактивный подход (баг → фикс → новый баг → фикс) — плохая практика.
Но слепое заполнение матрицы ради количества — тоже плохая практика.

### Опциональные зависимости

Если функция принимает опциональный параметр — тестируй путь БЕЗ него. Побочные эффекты (email, логи) могут не срабатывать — это должно быть явно проверено, если влияет на поведение.

## Формат промпта тестировщику

Конкретные тест-кейсы:
1. Что тестируем — модуль, функция (ссылка на REQ/инвариант)
2. Риски (`P0/P1/P2`) и почему они важны
3. Сценарии — таблица: ввод → ожидаемый результат
4. Для каждого сценария: какой риск он ловит и почему существующие тесты это не ловят
5. Какие существующие тесты нужно удалить или переписать, если они закрепляют уже запрещённое поведение
6. Что сознательно НЕ тестируем и почему
7. Регрессии — какие существующие тесты прогнать

## Обязательная секция в каждом промпте

```md
## ⚠️ Перед началом работы
1. Прочитай `.claude/roles/<роль>.md` — это твоя роль
2. Когда закончишь: git add <файлы> && git commit -m "[tester] ..."

```

Без этой секции промпт не отправляется.

## Именование промптов

Формат: `<тип>-<краткое-название>-<P>-<роль>.md`
- `<тип>` — `func` (функциональный) или `op` (операционный)
- `<краткое-название>` — суть задачи через дефис
- `<P>` — порядковый номер промпта в цикле (1 = тестировщик, 2 = кодер, ...)
- `<роль>` — `tests` или `code`

Примеры:
- `func-stale-suppression-1-tests.md` — функциональный, тесты
- `op-fix-mock-setup-1-tests.md` — операционный, тесты

Префикс принудительно заставляет классифицировать промпт ДО написания. Если не можешь уверенно поставить `op-` — ставь `func-`.
